# Herdr 使用剧本：一个主管、两个 worker，演练迁移到达梦

这份说明按本仓库的合体版 `herdr-planning-files` 编写。你只需要这一个 skill，不必再单独调用 `herdr-peers`。以下是操作剧本，没有实际创建 pane，没有连接服务器，也没有执行迁移。

这里把“迁移达梦服务器”理解为：现有应用的数据从原数据库迁到达梦数据库，应用也改为连接达梦。如果还要搬应用服务器、域名、文件存储或整套机房，要另加这些任务，不能默认已经包含。

## 先看懂标记

| 标记 | 谁来做 | 你要不要复制 |
| --- | --- | --- |
| **【你发送 → 主管】** | 你把提示词发到主管 pane | 要，按当前步骤选一条 |
| **【自动消息：主管 → worker】** | 主管用内置通信工具发送 | 不要；这是你用来核对的预期行为 |
| **【模拟回报：worker → 主管】** | 演练中由 worker 回报 | 不要把它当成实际检测结果 |
| **【你发送 → worker】** | 少数情况下，你直接找某个 worker | 仅对应情境使用 |
| **【生产模板】** | 正式迁移前填写并确认 | 演练时不要发送；未填完不能执行 |

下面自动消息展示的是正文。实际投递时，工具还要带上 PLAN_ID 和协议标记，接收方保留完整消息并先做 `check`。不能只在自己的回答里写“已通知”，却没有调用工具。

正文里的数字、故障、结果和业务背景都是虚构的演练材料。真正运行时，只有命令输出、测试报告和人工确认才能成为证据。

第一次用，可以先走第 2、3、4、6、7、9 节，体验建队、分工、进度、阻塞和改方向；想少发消息，建队后直接用第 24 节。其余故障场景按需要插入，不必一次全部发生。场景切换时，沿用实际生效的计划和文件 owner，不把上一分支的假设当成下一分支的事实。

## 1. 三个人怎么分工

| 角色 | 本例使用的 agent | 负责什么 |
| --- | --- | --- |
| 主管 main | 当前 pane 里实际运行的 agent | 拆任务、维护公共计划、处理冲突、向你提问、汇总证据和验收 |
| worker1 | Claude Code | 数据库对象、数据迁移路径、数据核对、数据库侧切换与回退草案 |
| worker2 | OMP | 应用兼容性、业务回归、性能检查、应用侧部署与运维准备 |

worker1、worker2 是角色名。实际 pane 地址由新框架返回，不照抄以前测试里的地址。这个结构总共是三个 pane，两个 worker 不包含主管。

你通常只和主管说话。worker 可以直接沟通技术细节，但不能私下扩大任务范围或修改别人负责的文件。需要决定业务取舍时，回到主管，由主管问你。

## 2. 一句话建队

先进入你要使用的 Herdr workspace，在准备保留的主管 pane 里发送：

**【你发送 → 主管｜建队】**

> 使用 herdr-planning-files，保留你作为主管，新增两个 worker：worker1 用 Claude Code，worker2 用 OMP。只初始化，完成后告诉我角色与 pane 对应关系、实际耗时，再等我发任务。

本句沿用当前 workspace 和项目目录，不另建 workspace。想隔离演练，先进入一个专门的测试 workspace，再发这句话。

主管应返回 PLAN_ID、PLAN_DIR、成员对应关系、启动耗时和未验证项。`ready` 只表示启动与身份检查通过，尚不能证明业务完成或三个模型已经通信成功。

如果这里卡住，先处理初始化问题，不要反复再发建队命令。恢复应沿用原计划和原 pane。

## 3. 给主管一个足够清楚的任务

**【你发送 → 主管｜开始演练】**

> 我们用“现有生产系统迁到达梦”练一次协作流程。先不碰真实服务器，只允许在这次 PLAN_DIR 下写演练文件，以及在本框架里通信。
>
> 背景都是假设：源库 Oracle 19c，目标 DM8，具体补丁版本待确认；应用是 Java，通过 JDBC 访问数据库。数据量按 500GB、300 张表估算，里面有存储过程、定时任务、大字段和第三方接口。允许停写窗口暂定 30 分钟，已经提交的交易不能丢。
>
> worker1 负责数据库，worker2 负责应用和验证。你负责总计划、进度和需要我决定的问题。先列出缺少的信息，再把可以独立做的事情分出去，别因为一个版本号没确认就让所有人等着。
>
> 按上述假设做桌面演练。模拟输入和模拟结果都标 SIM；没有实际运行的测试写“未实测”，不能写“通过”。先完成现状梳理和分工，后面的故障由我逐步给你。

这里刻意没有规定“必须用某一种迁移工具”。两个 worker 要核对实际版本、支持范围和环境条件后再提出方案。上述产品名不代表这些版本组合已经验证兼容。

**【主管应该问你的问题｜示例】**

> 我先把缺口列出来：两个数据库的完整版本、字符集和排序规则、应用依赖及驱动版本、数据日增量、业务高峰、外部读写入口、可接受停机和恢复时间、账号权限、谁能批准停写与恢复。
>
> 我会让 worker1 先做数据库调查表，worker2 先列应用检查项。现在最需要你定两件事：30 分钟是硬上限吗？如果演练发现做不到，是延后迁移，还是可以申请更长窗口？

**【你发送 → 主管｜补充演练条件】**

> 30 分钟先按硬上限处理，做不到就拿证据回来讨论，不许自己改成 60 分钟。完整版本、字符集和插件清单都记为待确认。当前只做本地演练，生产只读访问、测试库写入、生产切换要分别申请。需要我拍板时，把问题和影响放在同一条消息里。

## 4. 主管怎样把任务分出去

主管先在 `task_plan.md` 登记任务、交付物、验收条件和唯一 owner，再发消息。下面这些业务文档由本例约定，不是 skill 自动生成的固定文件。

所有路径都相对于本次 `PLAN_DIR`。

| 任务 | owner | 交付文件 | 本阶段验收 |
| --- | --- | --- | --- |
| DB-01 数据库调查与方案 | worker1 | `deliverables/db-assessment.md` | 已知、未知、版本核对项、迁移选项、风险和所需权限分开写 |
| APP-01 应用调查与验证设计 | worker2 | `deliverables/app-assessment.md` | 数据库依赖、核心业务链路、改造点和验证办法明确 |
| DB-02 数据一致性验证 | worker1 | `deliverables/db-validation.md` | 定义核对范围、口径、差异处理；模拟与实测分开 |
| APP-02 业务与性能验证 | worker2 | `deliverables/app-validation.md` | 写清用例、基线、结果、遗漏和失败证据 |
| DB-03 数据库切换草案 | worker1 | `deliverables/db-cutover.md` | 停写、同步收尾、核对、失败分支和新写入处理写清 |
| APP-03 应用切换草案 | worker2 | `deliverables/app-cutover.md` | 入口、任务、连接池、依赖、观察与恢复步骤写清 |
| MAIN-01 决策、总步骤与验收 | 主管 | `deliverables/decisions.md`、`deliverables/runbook.md`、`deliverables/acceptance.md` | 每个决定有范围，每一步有负责人、前提、证据和停止条件 |

公共的 `task_plan.md`、`progress.md`、`findings.md` 由主管维护。worker1、worker2 分别写自己的 `workers/worker1.md`、`workers/worker2.md`。原始材料分别放到 `evidence/worker1/`、`evidence/worker2/`，避免覆盖。

**【自动消息：主管 → worker1｜notify，分派长任务】**

> DB-01，计划 v1。你负责数据库调查，交付 deliverables/db-assessment.md，只写这份文件和你的日志、证据目录。先查清需要哪些对象、版本和数据特征信息，再比较可选迁移路径。
>
> 当前只有虚构背景，没有服务器访问授权。拿不到的信息标“待确认”，别补成事实。完成第一轮调查表就汇报；如果发现会影响 30 分钟窗口的条件，先报阻塞，不要等整份报告写完。

**【自动消息：主管 → worker2｜notify，分派长任务】**

> APP-01，计划 v1。你负责应用依赖和验证设计，交付 deliverables/app-assessment.md，只写这份文件和你的日志、证据目录。列出 SQL、驱动、事务、连接池、后台任务、报表和外部接口要检查的地方，挑出必须先验证的业务链路。
>
> 这轮不改业务代码，不连接服务器。需要数据库细节，可以向 worker1 问一个短问题；如果答案还没有，就记录依赖，继续做不依赖它的部分。

接到任务的 worker 可以独立 `notify` 一次“已接单，当前做什么”。主管不用再回“收到你的收到”。这次接单回报也能帮助核对通信是否实际到达。

## 5. 两个 worker 怎么直接沟通

短问题用 `ask`；收到完整消息先 `check`，判定为 `answer` 后才可以 `reply` 一次。

**【自动消息：worker2 → worker1｜ask】**

> APP-01 需要确定金额字段的验证口径。当前是否已有字段精度、舍入规则和空值处理的材料？有的话给我文件位置，没有就告诉我还缺什么。

**【模拟回报：worker1 → worker2｜reply】**

> 目前没有实际字段定义。db-assessment.md 已把精度、舍入和空值规则列为待确认，你先设计覆盖这些情况的用例，别按“默认保留两位”写死预期。

这段问答解决信息缺口，不变更任务范围。若问题需要主管或你拍板，worker 先把已收到的 ask 答清楚“未确认，需要主管决定”，再另发通知给主管；不要拿着一个未回复的 ask，又对别人发 ask，形成相互等待。

长调查、代码改造和数据核对都用 `notify` 分派，不能用一个 ask 挂住整项任务。

## 6. 你怎么问进度

**【你发送 → 主管｜进度查询】**

> 帮我查一下两个 worker 的实际进度。分别告诉我：做完了什么、证据在哪、现在卡在哪、接下来做什么、有没有需要我决定的事。没有新回报就说没有，不要只给一个百分比。

**【自动消息：主管 → worker1、worker2｜分别 notify】**

> 请各自用一条独立 notify 回报当前任务的状态：已完成项、证据路径、正在做的事、阻塞和需要谁处理、下一步。区分实际检查与 SIM 演练。简短说明就好，不要为这次问进度重写整份报告。

这里用通知收集进度，两个 worker 各自报告，不做协议 reply，也不互相等待。只问一个人的短问题可以用 ask；上一段问答没结束前，不再发起另一段 ask。

**【模拟汇总：主管 → 你】**

> worker1 已整理数据库调查表，完整版本和数据变更量还没有材料，迁移路线暂时不能定。worker2 已列出订单、支付回调和日结三条优先验证链路，驱动兼容性未实测。
>
> 两份文件都已落盘，里面的业务背景是 SIM。现在没有实际迁移结果。需要你处理的是完整版本信息；其余调查可以继续。

如果对端还没回，主管应说“消息已提交，尚未收到回报，当前只能引用某时间的日志”，不能把旧日志冒充刚问到的进度。

## 7. 模拟权限不足：卡住一部分，不是全员停工

**【你发送 → 主管｜注入故障 1】**

> 加一个 SIM 场景：worker1 拿到的数据库调查材料不含对象定义，账号权限也不足以查询。请让它按真实流程上报。先别替我答应申请高权限账号，我要看它怎么说明影响、你怎么向我提问。

**【模拟回报：worker1 → 主管｜先写个人日志，再 notify】**

> DB-01 阻塞，编号 BLOCK-01。SIM 材料里没有存储过程定义，现有权限也拿不到，所以这部分不能判断是否需要改造。缺什么、影响哪些结论，已写在个人日志和 db-assessment.md。
>
> 我可以先完成表、字段和已知数据特征的调查表。请决定是让 DBA 提供脱敏后的对象定义，还是申请限定范围的只读查询权限；不需要先给我管理员账号。

**【主管 → 你｜提出具体选择】**

> 缺少对象定义，数据库改造工作量现在没法估。可以让 DBA 导出指定对象的定义，或者给临时账号开放必要的只读查询。第一种不用给 agent 接入账号，但材料更新要靠 DBA。你选哪种？

**【你发送 → 主管｜人工决定】**

> 选 DBA 提供脱敏对象定义，记为 DEC-01。先不申请额外数据库权限，也不允许 agent 连接生产。把要导出的对象范围列给 DBA。worker1 继续不依赖这些定义的调查，拿到材料后再补结论。

**【自动消息：主管 → worker1｜notify】**

> DEC-01 已记录：对象定义由 DBA 提供，你不申请额外权限、不接入生产。继续完成其余调查，把待补部分单列出来。APP-01 需要这些结果时，告诉 worker2 哪些结论目前不能使用。

这次批准的是“按该方式取材料”，不是“批准迁移”。主管要把决定、适用任务和仍未获准的操作写入决策记录。

## 8. 依赖没齐，worker2 怎么继续

**【自动消息：worker1 → worker2｜notify】**

> APP-01 依赖的存储过程定义还缺，相关改造结论暂不能用。数据库调查表里已标明哪些信息缺失，目前没有可靠的存储过程返回值材料。

**【模拟回报：worker2 → 主管｜notify】**

> APP-01 的存储过程调用验证等 DBA 材料。我先整理接口回归、异常处理、连接中断后的行为和后台任务清单。这部分不需要那份定义，预计下一次回报给你用例草案；实际执行时间现在还估不准。

worker2 继续的是主管已经分派的 APP-01，worker1 只提供信息，不给它增加任务。主管应拆开可继续的子任务和受阻子任务，不能只给整个任务写一个“blocked”。

## 9. 你临时改方向，怎么传到各个 pane

**【你发送 → 主管｜改变优先级】**

> 调整一下：先验证订单、支付回调和日结，历史报表后移。本轮先做测试环境演练，不排生产切换。请把计划改成 v2，通知两个 worker，并分别确认他们已经按 v2 做事。

**【自动消息：主管 → 两个 worker｜分别 notify】**

> 计划改为 v2：优先订单、支付回调和日结，历史报表后移。当前阶段只做测试准备与演练，不安排生产切换。各自重读 task_plan.md 的 v2 范围，日志里标出正在执行的任务版本。已做好的其他材料保留，不继续扩展。采用后各发一条独立 notify，告诉我所用版本、下一步和停下的旧任务。

**【模拟回报：worker2 → 主管｜独立 notify，确认采用新范围】**

> 已读 v2。下一步先补订单和支付回调用例，历史报表优化停下，保留已有调查结果。没有开始生产操作。

计划版本是这个项目约定的记录方式，不是通信工具自带的强制版本锁。只改主管回答或只改文件，不会自动让所有 worker 立刻看到。涉及方向变化，要更新记录、通知，并核对是否已采用。

## 10. 两人想改同一份文件

**【你发送 → 主管｜注入故障 2】**

> 加一个 SIM 场景：两个 worker 都想修改最终切换手册。请处理文件归属，保留双方意见，但别让他们同时覆盖同一份文件。

**【自动消息：主管 → 两个 worker｜notify】**

> runbook.md 继续由我维护。worker1 把数据库步骤写入 db-cutover.md；worker2 把应用步骤写入 app-cutover.md。引用具体章节提建议，我来合并，谁都不要直接覆盖总手册。

如果确实需要移交一个文件，顺序是：原 owner 停止写入并报告最后状态，主管更新归属，新 owner 确认接手后再编辑。旧 owner 未确认停笔时，不能只改一下表格就让新 owner 开始写。

**【你发送 → 主管｜让它完成交接】**

> 把 app-cutover.md 从 worker2 移交给 worker1。先让 worker2 停笔，列清未完成项和最后修改位置；你更新 owner 后再通知 worker1 接手。已有修改先保留，不要为了交接清空文件。

这是文件交接，不是替换 pane 或变更会话身份。

## 11. 两个 worker 的结果对不上

**【你发送 → 主管｜注入故障 3】**

> SIM：worker1 说订单表行数一致，worker2 说同一批订单的金额汇总不一致。不要直接判谁对，先组织核对口径，再给我结论。

**【自动消息：主管 → worker1｜notify】**

> DB-02 出现差异，先保留现有报告。补充你核对的时间点、范围、过滤条件、字段和方法。行数相同先只记为“行数检查通过”，不能据此写“数据完全一致”。

**【自动消息：主管 → worker2｜notify】**

> APP-02 保留金额差异样本和原始查询口径，标明数据时间点、状态过滤、币种、精度与舍入处理。这是 SIM，样本使用虚构数据。先验证是否在比较同一批数据，不要直接修数据。

**【模拟回报：主管 → 你】**

> SIM 核对发现，两边取数时点不同，worker2 还排除了取消订单，所以现有结果不能直接比较。我让他们统一范围和时间点后复核。当前状态是“验证口径未对齐”，没有批准数据修正，也没有宣布迁移成功。

复核仍有差异，再拆出数据类型、转换规则、应用计算、时区等具体原因逐项查。不要用两个 agent 投票代替证据。

## 12. 遇到失败，先保留现场，再考虑重跑

**【你发送 → 主管｜注入故障 4】**

> SIM：worker1 的一次测试导入执行到一半失败了，目标测试库可能已经写入了一部分数据。让它先报状态，别直接从头重跑。

**【模拟回报：worker1 → 主管｜notify】**

> DB-02 失败，SIM 现场已记录：最后一个已确认步骤、可能写入的范围、错误信息、未知部分。现在不确定是否有重复写入风险，不能直接重新执行整批导入。
>

## 14. “通知发了”不等于“对方处理了”

**【你发送 → 主管｜发现 worker 没响应】**

| 看到什么 | 应该怎么说、怎么做 |
| --- | --- |
| `submitted`，没有新回报 | 只能说工具已提交，不能认定对方已阅读；核对对端和日志 |
| `delivery_unknown` | 可能已写入终端，也可能未到达；先查现场和记录，再决定是否需要重发 |
| 对端正在忙 | 不承诺立即打断；急事要说明未获得执行状态确认 |

| 同一个 TASK_ID 重复出现 | 核对版本与已完成步骤，不因重复消息重复执行业务操作 |

**【模拟汇总：主管 → 你】**

> 最终核对未通过，目标尚未开放写入。建议按已批准的暂停条件停在这里。要恢复源端服务，仍需核对源端可用性、入口和任务状态，并按既定恢复步骤执行，不能只说“切回去就行”。

**【你发送 → 主管｜注入故障 7：目标已有新写入】**

> 换一个 SIM 分支：目标库已经接收了 20 笔新订单，随后出现严重故障。让团队说明怎么处理，不能直接切连接串回源库，把这 20 笔订单丢掉。

**【主管 → 你｜模拟情况报告】**

> 目标已有新交易，不能套用开放写入前的回退办法。先按批准的故障分支控制新增写入，保留目标库及相关日志，查清成功、失败和状态不明的请求，并核对第三方是否已产生扣款、通知等结果。
>
> worker1 负责列出数据差异及可恢复范围，worker2 负责业务请求、外部副作用和重复处理风险。是否原地修复、向源端补回数据，或延长停机，需要拿到这两份证据后由授权负责人决定。未经验证，不把反向同步当成现成能力。

**【你发送 → 主管｜人工决定，仅 SIM】**

> 演练里先选择暂停新增写入、保全数据，评估原地修复。回退批准暂不包含这 20 笔交易的反向写回。把每个方案可能丢失、重复或需要补偿的交易讲清楚，再由我和业务负责人选。

这个分支要检查数据库之外的结果，例如支付、消息、文件和第三方调用；恢复数据库并不等于外部动作也被撤销。具体处理办法仍须结合真实系统验证。

## 22. 人工暂时不在，或者你说“先停一下”

**【你发送 → 主管｜暂离】**

> 我接下来一小时不在。已批准的本地调查和文档整理可以继续。涉及生产访问、测试库清理、数据修正、切换或扩大权限的决定，列入待确认后停在那个步骤。能独立做的继续，不要把我没回复当成同意。

**【你发送 → 主管｜暂停】**

> 先暂停当前任务。通知两个 worker 在安全停点结束当前动作，不再开始新步骤；分别回报最后完成项、正在进行的操作和需要保留的现场。把计划标为暂停，我回来后再决定下一步。

主管要区分“暂停通知已发出”和“两个 worker 都已确认暂停”。如果某个工具或模型还在运行，通信本身不能保证立即中断；高风险操作的停止办法必须在执行方案里预先写明，并由有权限的人按方案处理。

**【你发送 → 主管｜恢复】**

> 恢复前先核对暂停点、两个 worker 的当前身份和最新日志，确认外部环境有没有变化。只继续原来已批准且仍有效的范围，有失效前提先回来问我。

## 23. 完成以后，还有什么不能漏

**【你发送 → 主管｜收尾】**

> 准备验收交接。给我：完成了什么、证据在哪、遗留问题谁负责、观察期看哪些指标、告警给谁、备份和恢复怎么交接，以及旧库什么时候才可以退役。演练结果和真实结果分开，未获准的清理动作不要做。

主管至少汇总：

- 技术验证与业务负责人验收是否都完成；异常用例和高峰表现是否仍有缺口。
- 监控、告警、定时任务、备份和恢复职责是否已经交给实际运维人员。
- 观察期、问题升级联系人、后续回退或修复办法、未关闭风险及其接受人。
- 旧环境保留多久、谁批准退役、数据和日志保留要求；不因测试成功自动删除旧库。
- 临时权限和测试数据什么时候回收；需要有批准的对象范围。

“团队任务结束”“业务验收通过”“旧库允许删除”是三件不同的事，不能用一个完成状态替代。

## 24. 想一次把整个协作过程演给你看

前面分步走，适合你自己体验。已经建好三个 pane，想少发消息，可以发下面这一条。

**【你发送 → 主管｜完整桌面演练】**

> 沿用当前 herdr-planning-files 框架，用一个主管、worker1 和 worker2 演练“现有生产数据库迁到达梦”。不连接任何服务器，不执行数据库操作，只在本次 PLAN_DIR 下写演练文件，并通过内置工具实际通信。
>
> 虚构背景：Oracle 19c 到 DM8，完整补丁版本待确认，Java/JDBC 应用，500GB、300 张表，停写窗口上限 30 分钟，已提交交易不能丢。这些是演练条件，不是实际环境信息。
>
> worker1 负责数据库，worker2 负责应用和验证。先登记任务、唯一文件 owner、交付物和验收条件，再分派。按顺序演示：接单，worker 间短问答，进度查询，材料缺失导致的阻塞，向我请求决定，调整计划并确认收到，结果冲突后的复核，失败后的现场保留，切换前 No-Go 判断。之后分别演示条件补齐的成功分支，以及目标库已有新写入时的故障分支，不把两个分支的状态混在一起。
>
> 所有环境信息、故障、指标和结果都标 SIM。不能把虚构测试写成通过。遇到需要我决定的节点就提出一个具体问题，受影响的步骤等我回答；独立且已授权的工作继续。不要替我编造批准，也别连续抛十几个问题。
>
> 通信必须真的调用工具，并记录投递状态。没有回应就说明未确认，不要把自己写的对白当成 worker 回答。最后给我一份复盘：我发了什么、任务怎样流转、哪些通信成功、哪些未确认，以及正式迁移还缺哪些材料。

这会真实测试本地团队协作，但仍不是数据库迁移测试。不要把整个指南一次塞进所有 worker；由主管分派他们需要的部分即可。

## 附录 A：通信命令长什么样

通常让 agent 自己执行。下面是方便你理解和排查的接口，不需要你手动做每次消息转发。

`COMMUNICATION_SCRIPT`、`PLAN_DIR` 和 `ROLE` 必须来自当前框架 context 的实际值；不保证它们已是 shell 环境变量。各角色在自己的真实 Herdr pane 中执行，不能在主管 pane 冒充 worker。

安装到共享池后的统一入口是（实际执行使用 context 给出的绝对路径）：

```text
~/.agents/skills/herdr-planning-files/scripts/communicate.py
```

主管给 worker1 分派长任务：

```bash
python3 "$COMMUNICATION_SCRIPT" --plan-dir "$PLAN_DIR" --role main notify \
  --to worker1 --text 'DB-01：按 task_plan.md 的 v1 范围完成数据库调查表，证据先写个人日志，再通知我。'
```

worker1 向主管报告阻塞：

```bash
python3 "$COMMUNICATION_SCRIPT" --plan-dir "$PLAN_DIR" --role worker1 notify \
  --to main --text 'DB-01 被对象定义缺失阻塞，证据见 workers/worker1.md；其余调查继续，请决定材料获取方式。'
```

worker2 向 worker1 问一个短问题：

```bash
python3 "$COMMUNICATION_SCRIPT" --plan-dir "$PLAN_DIR" --role worker2 ask \
  --to worker1 --text '金额字段的精度和舍入规则有没有已确认材料？请给我路径，未知就直说。'
```

收到消息的 worker1 保存完整原消息，包括最前面的 PLAN_ID 和协议标记，再分类：

```bash
python3 "$COMMUNICATION_SCRIPT" --plan-dir "$PLAN_DIR" --role worker1 check \
  --message /绝对路径/完整收到的消息.txt
```

只有判定为 `answer`，才针对原消息回复一次：

```bash
python3 "$COMMUNICATION_SCRIPT" --plan-dir "$PLAN_DIR" --role worker1 reply \
  --message /绝对路径/完整收到的消息.txt \
  --text '目前未确认，待核对项在 deliverables/db-assessment.md。'
```

`notice` 是通知，记录并处理内容，不做协议 reply；`never` 不回复；`none` 不能拿来申请回复授权。长内容用 `--text-file` 指向完整正文文件。

工具会核对发送方与目标的身份并留下发送记录。它不会替你证明模型已读，也不会替数据库提供事务、权限隔离或业务操作的去重保证。

## 附录 B：怎么判断这次演练有没有达到目的

- 总共一个主管、两个 worker，实际角色与 pane 映射明确，主管采用了当前 context。
- 任务有唯一 owner，两个 worker 都有自己的交付与日志，公共计划由主管维护。
- 能找到真实的分派和回报记录，不是主管在一个 pane 里扮演三个人。
- 至少有一次经过 `check` 的短问答；通知没有演变成“收到”的循环。
- 至少有一次阻塞上报、你本人作出的限定决定，以及主管向受影响 worker 传达决定。
- 至少有一次计划调整后的接收确认，不能只看文件修改时间。
- 对消息未确认、结果冲突和环境身份变化，团队能停在合适的位置说明缺口。
- 结尾明确区分：协作实测、数据库模拟、仍未验证的事项。

耗时也分开记：从你发建队指令到主管给出建队报告，是用户看到的建队耗时；脚本自身耗时单列；业务演练和等你回答的时间另列。不能用脚本耗时替代整轮等待时间，也不能把修复与人工等待混进一次干净的启动性能结论。
